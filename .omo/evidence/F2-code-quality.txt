=== Findings ===

[1] MEDIUM — parse_explicit_prefix panics on multi-byte UTF-8 input
    crates/compass-core/src/data/symbol.rs:16-27 (byte-slicing code[..3] / code[..2]
    without char-boundary checks; eq_ignore_ascii_case branches)
    New exposure: crates/compass/src/main.rs:283 normalize_config_symbol →
    migrate_legacy_config (main.rs:296) runs at every startup on user-editable
    ~/.config/compass/config.toml values.
    Repro (standalone, same function body): parse_explicit_prefix("平安银行") and
    parse_explicit_prefix("贵") both PANIC ("end byte index 2 is not a char boundary").
    A config such as default_symbol = "贵州茅台" (stock name pasted in) crashes the
    GUI at startup instead of load_config's promised graceful fallback (the value
    previously flowed to validate_symbol which returned a clean DataError).
    Fix: use code.get(..3)/code.get(..2) (Option) or strip_prefix-based matching;
    add a non-ASCII regression test to the symbol.rs test module.

[2] LOW — exchange_of_symbol legacy fallback missing 92→BJ rule
    crates/compass/src/main.rs:459-471 (only 6→SH, 8→BJ, else→SZ) vs the canonical
    D10 heuristic in infer_exchange_prefix (main.rs:277-285: 6→SH, 8/92→BJ, else→SZ)
    and kb/design/symbols.md. Legacy bare "920001" in un-migrated parquet displays
    "SZ | 920001" (display-only, transitional data).
    Fix: delegate the bare fallback to infer_exchange_prefix(symbol).unwrap_or("SZ")
    or add a starts_with("92") branch so the two heuristics can't drift.

[3] LOW — strategy-layer exchange derivation diverges from GUI layer and parser
    crates/compass-strategy/src/lib.rs:120-126 (screen_symbol exchanges filter) and
    crates/compass-strategy/src/sepa/scoring.rs:976 (BJ hard filter) use case-sensitive
    starts_with("SH"/"BJ") with NO legacy bare-code fallback, while
    main.rs exchange_of_symbol keeps a fallback and parse_explicit_prefix is
    deliberately case-insensitive (symbol.rs tests assert lowercase acceptance).
    Consequences: (a) lowercase-prefixed symbols ("sh600519") mis-derive as SZ at the
    strategy layer (validate_symbol blocks them at the data layer, so defense-in-depth
    only); (b) on pre-migration bare parquet the screener SH filter drops 600519
    (classified SZ) and the SEPA BJ hard filter lets legacy bare 8xxxxx into ranking,
    while the GUI displays both correctly — the three layers disagree on whether bare
    data is supported (cli.md documents re-import as required, Metis B9).
    Fix: reuse parse_explicit_prefix at both strategy sites (case-insensitive by
    construction) and either restore the bare fallback for symmetry with the GUI or
    state explicitly in cli.md/symbols.md that the strategy layer requires re-imported
    prefixed data.
